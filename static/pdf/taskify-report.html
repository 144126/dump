Abstract

 

Task management is a crucial aspect of any productive activity; it makes clear what needs to 

be  done  to  achieve  specific  goals.  While  many  digital  tools  exist  for  this,  the  traditional 

pen-and-paper to-do list remains a common option. But, as many people have experienced, 

this method comes with its limitations: paper lists can be lost or damaged, are difficult to back 

up,  and  become  messy  with  edits.  Furthermore,  they  cannot  be  searched,  sorted,  or 

reorganised  efficiently.  Digital  to-do  lists  emerged  to  address  these  challenges,  making  it 

easier to manage tasks. The developed artefact, Taskify, builds on this concept by providing 

a system with unique features beyond the core functionalities of creating, editing, completing, 

deleting,  and  searching  for  tasks.  These  features  include  a  completion percentage tracker, 

postponing  tasks,  location-based  reminders,  routine  reminders,  and  more.  Built  on  a  solid 

architecture with a fast and powerful technology stack, the web application results in being a 

useful tool that can greatly improve the productivity of its users.

Chapter 1: Introduction 

1.1  The System Developed 

This  project  is  centred  on  the  development  of  Taskify,  a task management web application 

designed  to  serve  all  types  of  users,  from  students  and  teachers  to  business  owners  and 

everyday  individuals.  The  primary  problem  addressed  by  this  system  is  the  inefficiency  of 

managing  tasks  with  the  traditional  pen-and-paper  method.  This  method  creates  several 

drawbacks:  paper  lists  are easily lost or damaged, are difficult to back up, and do not have 

support for reminders or alarms. Furthermore, they do not sync across devices, offer limited 

space, and cannot be easily searched, sorted, or reorganised.

 

As  a solution, Taskify provides a digital platform where users can create, edit, and organise 

tasks that are securely backed up to the cloud and accessible from any device. Specifically, 

users will be able to make an account, log in and log out, add, edit, and complete tasks, flag 

tasks as important, delete tasks to trash, include task descriptions, add subtasks, categorise 

tasks  into  custom  task  lists,  and  search  for  tasks.  Future  updates  to  the  application  will 

introduce unique features that will make Taskify stand out from its competitors. 

1.2  Methodology & Framework Justification 

The  project  was accomplished using the Agile development methodology. This method was 

chosen primarily for its iterative approach to software development, as it supports the future 

intention to incrementally introduce new features or update existing ones. Alongside the Agile 

framework, object-oriented development principles were also used as a coding technique, for 

example, within TypeScript modules. 

1.3  The Solution that Emerged 

The  solution  that  emerged  was  a  web  application  developed  with  a  modern  technical 

architecture. The front-end of the system was built using the JavaScript framework, SvelteKit 

(v2.22.0),  powered  by  the  Svelte  language  (v5.0.0) and TypeScript. The user interface (UI) 

elements  were  developed  using  HTML5  and  CSS3.  For  the  backend,  SvelteKit  and 

TypeScript  again  handled  the  server-side  logic,  and  the  database  was  constructed  and 

managed  using  the  Qdrant  Vector  Database  v1.15.0.  To  ensure  a  stable  final  product,  the 

web application was tested for cross-browser compatibility across Google Chrome, Microsoft 

Edge, and Mozilla Firefox browsers during development.

4.2  Choice of Programming Language 

A  set  of  programming  languages  and  frameworks  was  chosen to build the app’s front-end, 

back-end, and database. They were selected for their ability to bring to life the project idea in 

the way it needed. This section will justify why those selections were chosen, beginning with 

the front-end. 

Front-end 

The front-end of Taskify was built using SvelteKit (v2.22.0), powered by Svelte 5 (v5.0.0) and 

TypeScript. HTML5 and CSS3 were used for the structure and styling. 

SvelteKit  was  chosen  because  it  is  a lightweight framework that emphasises speed. Unlike 

other  frameworks  that  use  a  virtual  DOM  at  runtime,  SvelteKit  compiles  components  into 

highly  optimised  vanilla  JavaScript  at build-time and updates the real DOM directly, making 

the  app  feel  instant  for  the  user.  Svelte  also  has  much  simpler  and  more  straightforward 

syntax to code with compared to other front-end frameworks. 

TypeScript  is  a  superset  of  JavaScript  that  adds  static  types.  It  lets  you  define  types  for 

variables,  functions,  objects,  etc.  TypeScript  was  integrated  to  provide  compile-time  type 

checking. Adding static type safety to JavaScript allowed me to catch errors and bugs while 

writing the code (compile-time and build-time), rather than discovering them later at runtime, 

because it makes sure I’m using the right kind of data in the right places. 

Back-end 

SvelteKit is a full-stack-capable framework, which means it could also handle the server-side 

logic  of  Taskify.  This was a major advantage because it allowed the entire application to be 

written in a single language, TypeScript. This made development much smoother because I 

didn’t  have  to  switch  contexts  between  different  languages  and  frameworks.  This  kept  the 

project  structure  clean  and  simple,  and  communication  between  the  client  and  server 

seamless.

Database 

Qdrant  is  an  open-source  vector  database  and  vector  search  engine  written  in  the  Rust 

programming language. It efficiently stores, indexes, and searches high-dimensional vectors 

(embeddings)  for  similarity  search,  semantic  search,  recommendation  systems,  RAG,  etc. 

Qdrant v1.15.0 was used to store Taskify’s data. While SQL databases are common for to-do 

lists, Qdrant enables embedding-based search. This means tasks can be searched based on 

their meaning, not just exact keyword matches, displaying in the search results tasks that are 

related in meaning to the search keyword. Additionally, its payload feature acts as a flexible 

key-value store, which makes filtering tasks fast (like showing only ‘Important’ or ‘Completed’ 

items). 

4.3  System Cutover 

The  system  cutover  from  the  development  architecture  to  the  implementation  would 

implement the immediate/big bang cutover strategy and the parallel cutover strategy because 

users  migrating  to  the  system  are  divided  into  two  types:  users  transitioning  from  the 

pen-and-paper  method  and  users  from  other  task  management  systems  like  Todoist  or 

Google Tasks. Users from pen and paper will use the immediate cutover strategy, where they 

immediately  discontinue  use  of  their  old  method  and  adopt  the new system by creating an 

account on Taskify and continuing to add and complete tasks as usual. 

Users from other systems, like Google Tasks, will transition with the parallel cutover strategy 

to help them properly migrate all their data from the old system to Taskify without disrupting 

their  productivity  flow.  For example, a user from Google Tasks, after onboarding on Taskify, 

will use Taskify along with their old system side-by-side. This is the "parallel running" phase. 

They may put new tasks in Taskify while still checking their old tasks in the old system. This 

method  will  involve  another  strategy,  the  user-driven  cutover.  This  means  the  user 

themselves  decides  when  to  fully  "cut  over."  This  happens  when  they  feel  comfortable 

enough with Taskify and have moved all their important data across. At this point, they stop 

using Todoist and use Taskify exclusively. 

Deployment  of  the  application  to  the  public  internet  for  users  to  access  will  be  done  by 

launching it with a reliable hosting service. The chosen hosting service to launch Taskify will 

be  Vercel.  Vercel  is  a  cloud  platform  built  specifically  for  modern  web  frameworks  like 

SvelteKit.  It  makes  launching  a  website  very  easy  because  it  connects  directly  to  a 

developer's GitHub account and automatically builds and deploys the application every time 

new  code  is  pushed,  making  the  process  of  getting the site online and updating it fast and 

simple.

In conclusion, the system cutover plan for Taskify is a user-relative adoption, supported by a 

data migration plan to make the switch easier. 

4.4  Data Migration 

To migrate all important user data from their old systems to the new system, Taskify, different 

strategies  can  be  employed.  For users transitioning from pen and paper, they would simply 

register  on  Taskify  and  transfer  all  uncompleted tasks from their paper list to a Taskify task 

list  manually.  For  users  transitioning  from  digital  systems,  the data migration plan currently 

available to them will be to use Taskify and their old system in parallel. They could do this by 

adding new tasks to Taskify and only tracking ongoing tasks on their previous system. After 

completing the ongoing tasks, the user can now fully use Taskify exclusively. 

Another  method  that  could  be  employed  and  would  make  data  migration  much  easier  for 

users would be to use a CSV (Comma-Separated Values) file import/export. The user would 

first go to their old app (like Todoist) and use its "Export" feature to save all their tasks as a 

CSV  file.  Then,  in  Taskify,  there  would  be  an  "Import  from  CSV"  feature.  The  user  would 

upload  their  file,  and  the  system  would  then  read  the  CSV  file,  and  for  each  row,  it would 

create a new task in the user's Taskify account. 

However,  this  approach  is  currently  unavailable.  Furthermore,  the  development  of  such  a 

feature  is  tricky  because  the  CSV  template  format  of  the  other  apps  will  differ.  Taskify  will 

have to intelligently import data from those templates to match its own. 

Therefore,  the  data  migration  plan  for  Taskify  is  (1)  Immediate  transfer  of  all  uncompleted 

tasks from paper lists to Taskify. (2) Adding new tasks only to Taskify and completing ongoing 

tasks on the old system until full adoption of Taskify. 

4.5  Training 

Since  Taskify  is  a  web  application  designed  for  the  general  public,  there  were  no  formal 

training  sessions.  Instead,  the  training  strategy  relies  on  the  system’s  simple  and  intuitive 

design,  an  onboarding  guide,  and  helpful  tips  across  the  app.  The  user interface was built 

using  familiar  patterns  and  layouts  found  in  other  similar  applications.  This allows users to 

quickly  learn  how  to  use  the  system  simply  by  exploring  it.  For  every  first-time  user,  an 

onboarding guide takes them on an overview highlighting the major sections of the app, and 

describing what they are and how to use them. The guide can be replayed again later if the 

user  ever  needs  it. Pop-up tooltips were also included in the interface to provide users with 

additional information on certain features, such as buttons and links.

5.4  Configuration Management

all project assets. In a development workflow where files and code change constantly, proper 

configuration  management  is  needed because you can easily overwrite important progress, 

misplace  supporting  files,  or  need  to  fall  back  to  a  previous  stable  version  [source].  This

This  approach  was  chosen  because  it  avoids  the  complexity  and  cost  of  heavy  enterprise 

configuration  tools  while  still  making  sure  that  every  file was backed up, changes could be 

tracked, and previous states could be restored without manual file clutter (like having multiple 

copies such as Report_v1, Report_v2).

Code Versioning:

 The

 directory operated as a local Git repository

were committed and pushed to the

and  store  document  files in the cloud, while GitHub was used to host the remote repository

Appendices 

Phase 1: Project Initiation and Planning (7 days) 

●  Developing the initial project idea 

●  Securing approval for the project idea from my supervisor 

●  Drafting the project proposal 

●  Securing supervisor approval for the proposal 

Phase 2: Analysis and Requirements Gathering (21 days) 

●  Conducting a review of existing solutions to inform the project's direction 

●  Gathering the system's functional and non-functional requirements 

●  Modelling  a  Use  Case  diagram  to  illustrate  the  interactions  between  users  and  the 

system 

●  Outlining the system’s architecture 

●  Modelling an initial class diagram to define the system's static structure 

●  Securing  supervisor  approval  for  the  completed  analysis  and  requirements 

documentation 

Phase 3: Designing the system (14 days) 

●  Modelling the final, detailed class diagram, supported by an appropriate narrative

 

●  Modelling a sequence diagram to describe the behaviour of a key system operation.

 

Phase 4: Implementing the system (42 days) 

●  Setting up the database schema using Qdrant Vector Store.

 

●  Implementing  the  backend  server-side  logic,  including  user  authentication  and  task 

management APIs.

 

●  Developing the front-end user interface and connecting it to the backend services.

 

Phase 5: Testing the system and fixing bugs (21 days) 

●  Performing  diverse  black-box  tests  to  verify  that  the  application's  features  work  as 

expected from a user's perspective.

 

●  Developing  and  documenting  unit  and  integration  test  scripts  to  validate  individual 

components and their interactions.

 

●  Identifying, logging, and systematically fixing any bugs, errors, or defects discovered 

during testing.

 

Phase 6: Final Documentation and Handover (14 days) 

●  Writing  the  final  project  report  by  fleshing  out  each  chapter  and  arranging  a 

comprehensive appendix. 

●  Ensuring the final source code is well-commented and clean. 

●  Preparing and delivering the final project presentation and demonstration.
